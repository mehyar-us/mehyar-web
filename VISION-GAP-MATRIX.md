## 3. Vision contradictions found in code

1. **Tabbed dashboard vs "one conversation canvas."** Vision: "One conversation canvas replaces tabbed views… they don't live in a separate 'dashboard maze.'" Code: `web/workday.ts` defines six views (`today|chat|feed|billing|connections|account`) with a tab bar. This is the single largest structural contradiction; Phase-2 workstream (f).
2. **"40+ vertical agent definitions" vs 5 runtime profiles.** Vision: "40+ agent definitions in `docs/verticals/`" and the CoS "knows the full vertical registry." Reality: 41 `.md` files exist (docs only — per the honesty rule, docs ≠ implementation); `src/verticals.ts` has 8 schema verticals but only 5 real content profiles (salon, restaurant, plumbing_hvac, dental, auto_repair) — pet_grooming/med_spa are thin entries, `other` is fallback. The adjacent-vertical map (`src/vertical-mapping.ts`) honestly admits "We don't have a dedicated X mode yet." Scope decision needed (§4).
3. **"Subagents for parallel work" has no runtime counterpart.** The Muse-table row promises subagents; the closest runtime construct is the scheduled `business-harness` reviewer (`src/business-harness*.ts`) — not parallel subagents. Either cut the row from vision copy or scope a Phase-3 agent architecture.
4. **"Payments" as a one-click connection.** Vision lists payments alongside calendar/phone; code only ships API-key *guides* for Square/Stripe (`src/connector-guides.ts` `authKind:'api_key'`), not one-tap OAuth.
5. **"Reviews" as a connection.** Vision lists reviews; no GBP reviews monitoring, review alerts, or review-reply code exists (only a GBP *connection guide*).
6. **"Money in/out" cards.** Vision promises money cards; the ROI dashboard derives revenue from an owner-entered `avgTicketCents` (`src/proactive.ts:396`), not from connected payment data. Honest, but not the vision's "money this week."
7. **"One cost dashboard" for the AI Gateway.** Vision promises it; `src/ai-gateway.ts` has caching/fallbacks/rate limits but no dashboard (only local usage tracking in `src/billing/usage.ts`).
8. **Council — verified GONE.** Zero matches for "council" in `src/`, `web/`, or the vision doc. The 2026-10-08 kill is complete; no contradiction. (Crew 5 UX-overhaul artifacts — briefing+suggestions stack, `web/business-workspace.ts` — are the surviving structure.)
9. **"Never presents more than three connections at once."** The CoS doc's rule is honored in spirit by card-dedupe (`CONNECTOR_CARD_DEDUPE_MS`) but no onboarding flow exists to enforce the ≤3 rule — moot until (a) ships.

## 4. Verticals: the "40+ docs vs 5 runtime profiles" scope decision

- **Facts:** 41 `.md` files in `docs/verticals/` (auto-services … wedding-planners + chief-of-staff); runtime schema = 8 (`salon, restaurant, plumbing_hvac, dental, auto_repair, pet_grooming, med_spa, other`); real content profiles = **5** (salon, restaurant, plumbing_hvac, dental, auto_repair), each with vocabulary, detectorParams (lapsed days, slow-day gaps, lead minutes, no-show lookback), tone, and SMS templates. pet_grooming/med_spa entries are thin; `other` is generic fallback. 17 adjacent trades map honestly onto the 5 (`src/vertical-mapping.ts`), explicitly telling the owner when there's no dedicated mode.
- **Decision for Phase 2:** Two defensible options. **Option A (S, recommended):** keep the 5 deep profiles + honest mapping, and align the copy — vision/chief-of-staff docs and any public claims say "5 deep vertical modes (+2 beta), 40+ business-type guides, honest mapping for the rest." **Option B (M):** promote 2–3 more profiles to full depth (pet_grooming and med_spa are already in-schema; a `food_truck` or `home_services` profile would each be ~60 lines of vocab + detector tuning + templates following the existing pattern). The mapping honesty mechanism makes Option B incremental and safe.
